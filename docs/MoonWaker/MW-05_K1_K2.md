## K1 — the coordinator broadcasts, screens subscribe

### Outcome
`RetainedStreamSessionCoordinator` delivers its immutable `Snapshot` to subscribers on the
main thread after every state change. Screens render the delivered snapshot; they no
longer call `RetainedStreamSessionCoordinator.snapshot()` / `state()` /
`hasAttachedPresentation()` from render or refresh paths. The UI status follows reality
without a manual refresh (user-visible effect of K1).

### Facts in the current code
- `RetainedStreamSessionCoordinator` (`app/src/main/java/com/limelight/stream/`) is all
  static synchronized methods; there is no listener API. `Snapshot` exists (line ≈136).
- `ConsoleActivity` reads `RetainedStreamSessionCoordinator.snapshot()` 23 times, plus
  `state()`, `hasAttachedPresentation()` ×3, `canResumeInstantly()` ×2, `canSwitchGame()`
  ×3, `canSwitchOrigin()` ×3 — mostly from rendering/refresh code. The mutating calls
  (`terminate`, `clearIfMatches`, `switchGame`, `parkForBackground`, `completeDirectTermination`,
  `isPreparingSwitchOwned`) stay in K1.
- `Game` reads `snapshot()` 18 times; its other calls are mutations owned by S07. K1 may
  subscribe `Game` too only where it polls for rendering/decisions that a snapshot
  replaces one-to-one; do not restructure S07's ownership.
- Threading: coordinator mutations happen from several threads; delivery must hop to the
  main thread (`Handler(Looper.getMainLooper())`), coalescing is allowed (deliver the
  latest snapshot, never an older one after a newer one).
- There is no Robolectric/androidTest. Tests are plain JUnit; design the subscription so
  it is testable with an injected executor/poster instead of a real `Looper`.
- Many existing unit tests assert on source text (`contains(...)` over `.java`). Update
  them minimally when a refactor moves text; do not add new text tests.

### Required shape
- New, small: a subscriber registry inside the coordinator (or a sibling class in the
  same package) with `subscribe(Listener) → returns the current snapshot immediately`,
  `unsubscribe(Listener)`, and a single `publish()` called at the end of every mutating
  method that changed state. Subscribers are held strongly only between
  `onStart`/`onStop` of a screen (MW-04 §6: no Activity capture past `onStop`).
- `ConsoleActivity`: one subscriber object (prefer a new class in `console/`, e.g.
  `ConsoleSessionSubscriber`, that owns the "last delivered snapshot" and the rendering
  calls it triggers; the Activity only wires it). Rendering paths read that snapshot
  instead of polling. Remove the now-dead polling helpers.
- No new static mutable state outside the coordinator. No change to what the snapshot
  contains unless a renderer genuinely lacks a fact it polled before; then add the fact to
  `Snapshot` (one owner), not a side channel.
- `ConsoleActivity.java` must not grow (MW-07): net lines ≤ current (17 645 at base).

### Acceptance
- JVM tests (new, behavioural): subscribe returns the current snapshot; a mutation
  publishes exactly once per change; nothing is delivered after unsubscribe; an older
  snapshot is never delivered after a newer one; a subscriber that throws does not break
  delivery to the others.
- `gradlew.bat --console=plain testNonRootDebugUnitTest assembleNonRootDebug
  -PdiscordSocialSdkDir=D:/Maladie/moonlight-android/local-sdk/discord-social-sdk-1.10.18687`
  (JDK 17: `set JAVA_HOME=C:\Users\Basia\.jdks\openjdk-17.0.2`) green.
- Device evidence (coordinator runs it on the BRAVIA, API 31): home status and the
  "resume"/"running" presentation update after a stream ends or is parked without pressing
  refresh; the seven protected hardening flows are not regressed (run later, cumulative).

## K2 — screens read only the broadcast snapshot

Start K2 only after K1 is accepted (coordinator's word), in the same worktree.

### Outcome
`ConsoleActivity` keeps no copy of session state: the `retainedStream*` fields
(`retainedStreamHome`, `retainedStreamSessionId`, `retainedStreamHostId`,
`retainedStreamProfileId`, `retainedStreamAppId`, `retainedStreamPlayniteGameId`, lines
≈357–362, 62 references) and the 34 `runningGameId` reads are gone; every decision that
used them reads the delivered `Snapshot` (or the host observation it carries). This closes
the unmet S06 criterion recorded in the plan.

### Rules
- Where a field held a fact the snapshot does not carry, add it to the snapshot with its
  single owner (MW-04 §3.1 axes: transport, presentation, host game observation, pending
  operation, actor, durable record) — never a second copy in the Activity.
- Behaviour must not change; this is a read-side migration. Any decision that turns out to
  depend on a stale copy is fixed by reading the snapshot, and gets a behavioural test.
- Same checks as K1; `ConsoleActivity.java` net lines must decrease.
