## Findings

### [P1] The deferred switch is not mapped through SessionOrchestrator's result contract

Design v3 section 3 says visible Console launches Game with the target play intent and does not call RetainedStreamSessionCoordinator.switchGame until Game attaches. Current ConsoleActivity.java:13860-13884 reaches switchRetainedProviderGame through SessionOrchestrator.Effects.closePreviousSession. SessionOrchestrator.java:469-523 calls that effect on its executor and interprets its CloseResult: REUSED calls returnToRetainedStream() (535-538), whose effect has no PlayIntent argument; CLOSED starts the normal fresh launch; CANCELLED stops routing; NEEDS_CONFIRMATION prompts replacement. The proposed attach-first route does not specify which outcome prevents those follow-on actions while preserving the target intent, cancellation and failure reporting. Returning REUSED before the switch is complete could launch an untargeted resume; returning CLOSED can launch a second connection. Game is singleTask (AndroidManifest.xml:243-252) but currently has no onNewIntent override, so the promised latest-undispatched-intent behavior is also new production wiring. Add SessionOrchestrator to the production-path map and define the exact dispatch/result contract from Console selection through attach to Game switch completion, including no-attach/launch failure and a second selection. Test the real orchestrator effect wiring, not just a runtime helper.

### [P1] A STARTING reservation must not be accepted as a started provider

Design v3 section 7 adds a PROVIDER_OWNERS entry in STARTING before gateway.startGame, then lets an adopting coordinator receive its eventual result. In today's ConsoleStreamTransitionCoordinator.java:383-390, onStreamConnected calls requestProviderGameStart. Its runProviderGameStart at 441-455 treats any matching owner returned by isOwnedByCurrentAttempt as an already reused provider, invokes onProviderGameStartAccepted and begins observation. isOwnedByCurrentAttempt at 907-912 currently checks only spec equality. Thus a new coordinator adopted while the old gateway.startGame is still blocked can take the reused branch and announce acceptance before that call succeeds or fails. Make STARTING/STARTED explicit in every owner lookup and callback path: STARTING joins the single in-flight result without accepting or starting again; only STARTED can take the reuse branch. On terminal cleanup, do not claim an exact stop succeeded until a verified process identity is available; current compensateProviderStart at 530-555 fails immediately without a token. Test onStreamConnected after adopt but before the held startGame returns, for both success and failure, plus terminal cleanup when start succeeds before the process becomes observable.

## Answer to the input-gate question

A runtime read/write lock is acceptable as an ordering mechanism if the packet send and held-state update are one short critical section, and detach's write lock fences them before neutral packets. NvConnection.java:600-629 calls MoonBridge native send methods synchronously, so a slow native call could delay Game's lifecycle thread while it waits for the write lock. Keep network/host operations and UI callbacks outside that lock; verify a blocked-send/detach interleaving and avoid an unbounded main-thread wait. This is an implementation risk to measure, not a reason to add another state machine.
