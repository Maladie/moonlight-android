# Session and host-contract guide

Use when changing session orchestration, Gateway integration, privacy, child access, or their ownership. These are product constraints and navigation hints, not a claim that every current implementation already satisfies them.

## Preserve separate facts

Transport, executing game, presentation, and actor entitlement are independent. A stale or unknown game observation must not erase a known live transport. A saved resume record does not prove that a connection exists. Status badges and game tiles should derive from reconciled observations, not independent guesses.

Home/app navigation and game-only stop retain the transport where required by the task. Switching games stops the old execution and starts the new one without replacing a healthy retained stream. Full quit terminates the local transport even when host cleanup cannot be confirmed; show unresolved cleanup truthfully. Cancelling a reconnect to a running game stops only the local transport: the game and its host stream stay resumable. Cancelling a game start or a desktop stream that revealed nothing closes the host stream it opened, also after the host granted it; a start whose permit was not used yet (or whose `acquire` answer was lost) is handed back with `control/operation/abandon` instead of being sent, and the host records as that start's stream only its own effect. Retry after a lost transport rebinds the stream while the host application runs and starts fresh once the host proves it closed; until that start succeeds the old record stays the handle for closing the session. Background warm-up must not undo an explicit quit. Process death and Activity recreation are different recovery cases.

How long a stream and a game have run is the host's fact (`correlation.stream_started_unix_ms`, `process.started_unix_ms` in `/session/observation`, see `host-services/gateway/TRANSITION_CONTRACT.md`); the client computes durations on the host's clock from the same answer. What a status line shows between observations (the game last seen running with a verified process, its minutes and the stream's) has one owner, the host projection `SessionModel` holds per actor/execution profile (`SessionStateResolver.ProjectionOwner`, changed only by model events: Gateway observations and host polls; readers render the frozen copy in the published snapshot) (`SessionSnapshot.Display`). It is display only: it is no part of the projection identity, it never feeds readiness, Play or close, and `fresh_for_ms` stays what decisions use. The held game ends with an observation that refutes it (idle, another game, a game not running), a termination boundary, an unreachable host, or 45 s (`STATUS_DISPLAY_MS`) without a confirming observation; each actor/execution profile has its own owner. The host status reads "Game running · <game>" only for an online host without a session status and only when the selected profile's library names that game, so a child profile never names a game outside its shared library; a child's owner also holds only a game the host gave it a process start for (its own live time session's), so a game its parent runs reads "Online". A live session's status shows the stream's time only when it names no game, beside a game only that game's; over 7 days (`MAX_STATUS_DURATION_MS`) no time. Durations are whole minutes: the status changes at most once a minute, and that tick updates the top bar and the host tile without a library render or an extra request.

## Ownership and correlation

Start with existing owners: `SessionModel` (`com.limelight.session`, process-scoped, one dedicated model thread) owns session state and the persistent session records; it is the only reader and writer of its package-private stores `SessionResumeManager` (reconnect material), `SuspendedSessionStore` (intentional suspension) and `HostSleepStateStore`. State changes are `SessionEvent`s; readers use its last published snapshot. `SessionOrchestrator` owns the one decision table "session state × user intent → action" (`SessionOrchestrator.transition`: Play, and Back/Cancel/Retry on the stream screen; Retry stays on a live stream and starts a game again only after the host reported that start failed), which `ConsoleActivity` and `Game` only execute and fence at effect time; `LaunchTransitionController` owns the cover, readiness and input hand-off and feeds those facts to the table; host `OperationJournal` for durable GameOps. Verify locations and current contracts before changing them.

Physical runtime may move behind an existing facade. Do not create a second durable journal or competing state machine. `Game` and `ConsoleActivity` should shed the touched domain responsibility, not donate it to another catch-all manager.

Bind asynchronous observations and effects to the identities they can affect: host, actor, execution profile, transport generation, operation/transition, and game/process identity. Fence late stop, ready, entitlement, and reveal results at effect time. A refused close says why (`host-services/gateway/TRANSITION_CONTRACT.md`): no record with no host application leaves nothing to do and is silent; no record with a running application may have left the stream; a superseded generation still names a running session, so a user's close is repeated once with the host's current binding, while of an abandoned start it (like another owner's stream) leaves nothing; to a user's close another owner's or a foreign stream is reported as such. A change of actor can require new authorization even when Windows profile and transport stay the same. Avoid inventing one universal ID for unrelated lifetimes.

The host operator ends a session from Host Control (tray, hotkey) only through the Gateway: a short-lived request file beside `gateway.json`, which local accounts overwrite in place and cannot delete, is the one local channel, and the Gateway closes the stream and the verified game as a host operation on its own stream record (`host-services/gateway/TRANSITION_CONTRACT.md`, "Close session from Host Control"). It waits for a control operation in flight instead of superseding it, ends a child's time session as the host's own ends do, and leaves a foreign streamer application alone. A game process it cannot confirm is left too: the stream alone is closed and the answer says the game may still run (`stream_closed_game_unconfirmed`). The same host operation closes a stream record that had no client transport and an idle provider for 10 minutes; a paused session whose game runs stays. Host Control never calls a Bridge to close anything. The TV learns of it through its ended transport and the refused old generation; do not add a second notification path.

## Privacy and authority

The privacy cover is cosmetic UX, not a security or privacy boundary. Automatic reveal needs the matching execution's readiness and fresh-frame evidence; input follows the same transition. Whenever readiness fails or stays uncertain while the transport delivers frames, the user is offered the manual reveal ("Reveal now") next to Cancel/Retry rather than being rejected. After any reveal, automatic or manual, the cover does not return within that transition or stream (a lost game window or later failure is only a notice); only a new user-started transition may cover again. UI teardown must not strand a terminal stop waiting for an invisible view.

Windows sign-in requires the selected profile's configured consent, credential availability, and successful readiness. Do not treat absent data or timeout as success. Device permission to request sign-in is not permission to inspect or log credentials.

A child profile is a presentation and policy facade over its parent's execution profile. It uses the same launch, stop, retained-stream, retry, recovery, settings and host-control mechanisms as the parent. The only child-specific product restrictions are the parent-defined game library, play time/window limits, no child-profile/schedule management, no Discord, and no microphone. For the parent's Windows session (unlock, sign-in and Fast User Switching) a child acts as the parent, under the parent's own conditions, once the parent has enabled automatic sign-in with a stored credential and the parent itself holds the `use_profile` and `remote_sign_in` grants on that same client (a child never does more on a device than its parent could); this grants no parent profile, game library or play time. Enforce the game grant and time policy at the host boundary, but do not create a second child-owned stream, provider or recovery lifecycle. Entitlement expiry must invoke the common whole-session termination even if Android is absent; a late time-policy effect must not terminate a newer parent or child actor generation. Never replace verified process identity with a process-name-wide kill.

Session recovery is not a parent-only privilege. On the same trusted TV client and execution profile, a child may close, hard-reset, reuse or take over the current MoonWaker session regardless of which actor opened it. Selecting a child profile alone has no session effect. If the running game is shared with that child, entering it adopts the existing game and transport and starts that child's time attachment. If it is not shared, it is absent from the child library; clicking an allowed game automatically performs the common full close without a prompt and then launches the selected game. Parent takeover stops child-time charging without stopping the game or transport. Child-to-child takeover transfers charging at the committed actor handoff. Keep the general client, execution profile, transport generation, actor epoch and observed-app fences so stale callbacks cannot affect another TV, execution profile or newer actor generation.

## Evidence

Use controlled clocks/orderings for races and assert forbidden effects as well as final state. A mock flag cannot prove a retained native stream, successful Windows sign-in, displayed frame, or real input routing. Use the assigned checkpoint's device evidence for those claims.
